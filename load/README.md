# ДЗ № 2 Заявки в службу поддержки



## 1 Подготовка в Ubuntu WSL

Нужны Python 3.14.4, Docker Engine с Compose и cgroup v2, k6 и py-spy.
Испытание выполняется с той же машины и под той же учётной записью, что и ДЗ № 1.
Распакуйте проект или переключитесь на ветку ДЗ № 2. В корне репозитория выполните

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt py-spy
python -m pytest -q
git rev-parse HEAD
k6 version
py-spy --version
```

Поставьте k6 по [инструкции Grafana](https://grafana.com/docs/k6/latest/set-up/install-k6/).
Если исполняемые файлы лежат вне `PATH`, укажите их через `K6_BIN`
и `PY_SPY_BIN`.

Скрипт поднимает отдельную базу в Compose-проекте `keppel_yura_dz2` на
порту 55432 и запускает приложение по адресу `127.0.0.1:8082`. Если порт занят,
скопируйте `load/.env.dz2.example` в `load/.env.dz2` и поправьте порты в копии.
Рабочее наполнение пересоздаётся в базе испытания перед каждой ступенью.
В нём 3 000 пользователей, 10 категорий, 75 000 заявок и 225 000 комментариев.

## 2 Зафиксированный профиль нагрузки

| Операция | Вес, % | Обоснование |
| --- | ---: | --- |
| `GET /api/meta` | 5 | Справочники нужны при открытии интерфейса и формы заявки. |
| `GET /api/tickets` | 39 | Сотрудник часто открывает очередь заявок и фильтрует её. |
| `GET /api/tickets/{id}` | 30 | Карточку открывают, чтобы прочитать обращение и историю. |
| `POST /api/tickets` | 9 | Клиент отправляет одну заявку на проблему, затем её просматривают несколько раз. |
| `PATCH /api/tickets/{id}/status` | 7 | Статус меняют, когда берут заявку в работу или закрывают её. |
| `POST /api/tickets/{id}/comments` | 8 | Сотрудник отвечает клиенту и уточняет детали. |
| `GET /api/summary` | 2 | Руководитель открывает сводку SLA периодически. |

Каждая итерация k6 отправляет один HTTP-запрос. Исполнитель
`constant-arrival-rate` задаёт число итераций в секунду независимо от времени
ответа. Смешанный сценарий за каждые 100 запланированных итераций выбирает
операции по указанным весам. Проверка HTTP Basic проходит в
`setup()` и исключена из показателей сценария. Заголовок Basic передаётся с
каждым запросом. Успешные коды — 200 для чтения и смены статуса, 201 для записи.
Порог выполнен при p95 строго меньше 500 мс и доле ошибок строго меньше 1 %.

## 3 Ступени по 30 секунд

Запустите сначала смешанный профиль, затем сводку. Подбирайте верхнюю частоту
по результатам и при необходимости продолжайте со следующей ступени. Для
повторных серий выбирайте новый каталог `--out`.

```bash
python -m load.run mixed --rates 1 2 4 8 16 32 64 128 --out results/dz2/mixed
python -m load.run heavy --rates 1 2 4 8 16 32 --out results/dz2/heavy
```

Смешанный прогон останавливается на первой ступени, где нарушен порог.
Для сводки продолжайте до предела, если p95 превысил 500 мс уже на 1 запросе
в секунду. После нарушения порога скрипт останавливает серию, если на
очередной ступени полезная частота выросла не более чем на 10% относительно
предыдущей. Сверьте значения p95, фактическую частоту и пропуски

На каждой ступени скрипт сохраняет

- `stage.json` с p50, p95, максимумом, процентом ошибок, пропусками и частотой.
  Фактическая частота — число попыток, завершившихся у клиента в активном
  окне, включая тайм-ауты, делённое на длительность окна. Полезная частота
  учитывает только ответы с ожидаемым кодом.
- `resources.csv` с секундными отсчётами CPU, памяти и `pg_stat_activity`.
  CPU считается от одного логического ядра. Для приложения записывается RSS,
  для PostgreSQL — память cgroup за вычетом неактивного файлового кеша.
- `server.log`, `k6.log` и `points.jsonl` для проверки кодов HTTP,
  доступа к базе и времени отдельных операций

## 4 Профиль, опыт с настройкой и планы SQL

Подставьте частоту, на которой сводка достигла предела, в первую команду.
Подставьте частоту первой нарушившей порог ступени смешанного профиля во
вторую. На стенде ДЗ2 это 4 и 128 запросов в секунду

```bash
python -m load.run heavy --rates 4 --seconds 20 --profile --out results/dz2/profile
python -m load.run mixed --rates 128 --workers 2 --out results/dz2/tuning
python -m load.explain --out results/dz2/plans.json
```

частотой 31 Гц под нагрузкой в `profile.txt`. Для опыта с настройкой меняется число процессов
Uvicorn с 1 на 2 на одной ступени. Следующий запуск по умолчанию использует 1.
`plans.json` содержит пять повторов `EXPLAIN (ANALYZE, BUFFERS)` для
